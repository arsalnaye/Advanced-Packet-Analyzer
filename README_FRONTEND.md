# PacketScope Frontend

The repository now includes a React + Vite dashboard and a small local FastAPI adapter for the existing C++ DPI engine.

## What is included

- **Overview:** PCAP upload, engine action, capture metrics, protocol distribution, application breakdown, and packet stream.
- **Packet explorer:** Search and filter decoded packet-header summaries.
- **Blocking rules:** Add, enable, pause, and remove IP, domain, and application rules.
- **Reports:** Detected domains/SNI, application metrics, and filtered-PCAP download.
- **Settings:** Adjust load-balancer and worker counts and verify the local API connection.
- **Backend adapter:** Runs `src/dpi_mt.cpp` with your selected rules and returns its DPI report. The packet table separately decodes classic Ethernet PCAP headers for source/destination, ports, protocol, timestamps, and frame sizes.

The initial screen shows clearly marked **demo preview** data until a capture is analyzed. No successful scan is simulated.

## Requirements

- Node.js 20+ and npm
- Python 3.10+
- A C++17 compiler (`g++` / MinGW, `clang++`, or MSVC `cl.exe`)

## Start on Windows (PowerShell)

Open a terminal in the project root, then start the API:

```powershell
cd backend
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -r requirements.txt
python -m uvicorn app:app --reload
```

The API automatically builds a compatible C++ engine into `backend/bin/` when no compatible binary is already available and a supported compiler is on `PATH`. If using MSVC, start the terminal from **x64 Native Tools / Developer PowerShell for Visual Studio** so `cl.exe` is available. Alternatively, follow the existing `WINDOWS_SETUP.md` and set `DPI_ENGINE_PATH` to the compiled `dpi_engine.exe`.

Open a second terminal in the project root and start the frontend:

```powershell
cd frontend
npm install
npm run dev
```

Open the local URL printed by Vite (usually `http://127.0.0.1:5173`). Keep the backend terminal running. The frontend proxies `/api` requests to `http://127.0.0.1:8000`.

## Quick smoke test with the bundled capture

Use the repository's `test_dpi.pcap` file through the Overview upload area. Use a capture you own or are authorized to analyze. On the first run, the API may compile the C++ engine before processing.

## API

- `GET /api/health` — local service status
- `POST /api/analyze` — multipart upload with `file`, `lbs`, `fps`, and JSON `rules` fields
- `GET /api/results/{analysis_id}/output` — download the filtered PCAP generated by the existing DPI engine

The API accepts classic Ethernet `.pcap` captures up to 100 MB. PCAPNG files and non-Ethernet link types are rejected with an explanation. Packet detail rows are limited to the first 250 records to keep the UI responsive; report counters are calculated across the entire capture.

## Notes / current limitations

- This is **offline PCAP analysis**, not a live NIC packet sniffer or system firewall. The rule editor affects the next analysis; it does not change live device networking.
- TLS/SNI and application classification depend on what the existing DPI engine can recognize in the provided capture. Encrypted payloads are not decrypted.
- The packet explorer displays decoded metadata, not full raw payload bytes.
- Analysis output files remain in `backend/results/` until manually removed. Do not upload sensitive captures to any shared or public deployment; this adapter is intended for local development.

Current rule limitation: the bundled DPI engine's blocking implementation supports IPv4 IP-address rules; IPv6 packet metadata can be listed, but IPv6 block rules are rejected rather than silently treated as working.
